# Phase 2 — LLM Internals

## Chapter 7: Transformer Architecture

### Part 3 — From Hidden Representations to the Next Token

We've learned how a Transformer processes text through multiple blocks. Now we need to understand **how all that processing becomes an actual word or token.**

This is one of the most important parts of understanding how an LLM generates text.

Let's use this input:

> The cat sat on the

Our goal is to understand how GPT predicts what comes next.

---

### 1. Step 1: Get the final hidden representation

After tokenization, embedding, positional information, and processing through all Transformer blocks, the model has a final numerical representation for each input token.

Conceptually:

```text
Input: "The cat sat on the"

Tokens:
["The", "cat", "sat", "on", "the"]

                 ↓
          Transformer
          Block 1 ... N
                 ↓

Final hidden representations:

"The"  → [numerical vector]
"cat"  → [numerical vector]
"sat"  → [numerical vector]
"on"   → [numerical vector]
"the"  → [numerical vector]
```

Each representation contains information processed from the token and its context.

**But which representation do we use to predict the next token?**

For a standard causal GPT, we use the final hidden representation at the last input position.

Why?

Because the last token, `"the"`, has access to the preceding context. Its final representation is used to predict what comes after the entire input.

```text
"The cat sat on the"
                  ↓
       Final representation
           of "the"
                  ↓
      Predict the next token
```

Remember: the model isn't simply looking up what word usually follows `"the"`. Its prediction depends on the context processed throughout the network.

### 2. Step 2: The language-model head

We now have a numerical vector representing the final input position.

Let's call it `h`.

Suppose the model has a hidden dimension of 4 for this simplified example:

```python
h = [0.6, -0.2, 0.8, 0.4]
```

These values are illustrative.

However, this vector cannot directly tell us which token the model should generate.

We need to convert it into scores for possible next tokens.

That's the job of the **language-model head**, also called the *LM head*.

Conceptually:

```text
Final hidden representation
             ↓
       Language-model head
             ↓
      Score for every token
             ↓
             Logits
```

The LM head is typically a learned linear projection from the hidden dimension to the vocabulary size.

For example, suppose our toy vocabulary contains only five tokens:

```text
["cat", "dog", "runs", "food", "outside"]
```

The LM head produces one score for each token.

In a real model, the vocabulary might contain tens of thousands or more tokens.

**Important distinction:** The LM head doesn't independently understand the sentence. It transforms the final representation into scores that the model can use to predict the next token.

---

### 3. Step 3: Logits — how strongly does the model score each candidate?

Suppose the LM head produces these logits:

| Candidate token | Logit |
| --------------- | ----: |
| cat             |  -1.0 |
| dog             |   0.5 |
| runs            |   2.8 |
| food            |   1.2 |
| outside         |   0.3 |

These are made-up numbers for learning purposes.

A logit is a raw score produced before softmax converts the scores into a probability distribution.

In this example, `"runs"` has the highest logit.

But there's a crucial distinction:

**A logit of 2.8 does not mean the model is 280% confident, nor does it directly mean a 2.8 probability.**

Logits can be negative, positive, large, or small. Their absolute values aren't probabilities.

They are scores used in the next step.

### 4. Step 4: Softmax converts logits into probabilities

Now the model applies softmax to the logits.

You already learned softmax earlier, so let's connect it to the complete architecture.

```text
Logits
  ↓
Softmax
  ↓
Probability distribution
```

For our example, softmax might produce:

| Candidate token | Approximate probability |
| --------------- | ----------------------: |
| cat             |                    1.3% |
| dog             |                    5.7% |
| runs            |                   57.1% |
| food            |                   11.5% |
| outside         |                    4.7% |

These numbers are only illustrative and don't exactly represent the softmax distribution for the listed logits.

The important idea is that softmax converts the scores into nonnegative values that sum to 1.

Each value represents the model's assigned probability for that candidate as the next token, given the current context.

Notice that the highest-scoring token generally receives the highest probability.

However, **the model doesn't necessarily select the token with the highest probability every time.** That depends on the decoding strategy.

---

### 5. Step 5: Select the next token

The model now needs to choose a token.

There are different decoding strategies.

**Greedy decoding**

Selects the token with the highest probability.

For our example:

```text
runs → 57.1%
```

So the model chooses `"runs"`.

**Sampling**

Samples a token according to the probability distribution. A lower-probability token can sometimes be selected.

Sampling introduces variation into generation.

Temperature and methods such as top-k and top-p can influence how sampling works. We'll study these in detail in our generation chapter.

For now, remember:

* Logits are raw scores.
* Softmax produces probabilities.
* Decoding determines how the next token is selected.

---

### 6. Step 6: Append the selected token and repeat

Suppose the model selects `"runs"`.

The generated sequence becomes:

```text
Original input:
"The cat sat on the"

Selected token:
"runs"

Updated sequence:
"The cat sat on the runs"
```

The model then processes the expanded context to predict another token.

For example:

```text
"The cat sat on the"
          ↓
Predict "runs"
          ↓
"The cat sat on the runs"
          ↓
Predict the next token
          ↓
Continue...
```

The example sentence isn't intended to be a grammatically sensible completion. We're illustrating the mechanics of generation.

The process continues until a stopping condition is reached, such as generating an end-of-sequence token or reaching the output-length limit.

In practice, efficient implementations often use a **KV cache** to avoid recomputing attention keys and values for the entire previous sequence at every generation step. We'll cover that when we study generation.

---

## 7. The complete picture

Let's connect everything you've learned in Phase 2.

```text
                 INPUT TEXT
                     │
                     ▼
                Tokenization
                     │
                     ▼
                  Token IDs
                     │
                     ▼
              Token Embeddings
                     +
             Positional Information
                     │
                     ▼
            TRANSFORMER BLOCKS
                     │
          ┌──────────┴──────────┐
          │                     │
     Self-Attention        Feed-Forward
          │                     │
          └──── Residuals ──────┘
                     │
              Normalization
                     │
                     ▼
           Repeat across layers
                     │
                     ▼
        Final Hidden Representation
          at the Last Input Position
                     │
                     ▼
          Language-Model Head
                     │
                     ▼
                   Logits
                     │
                     ▼
                  Softmax
                     │
                     ▼
               Probabilities
                     │
                     ▼
             Decoding / Selection
                     │
                     ▼
              Next Token Added
                     │
                     └───────────────┐
                                     │
                       Predict Again ┘
```

This is the fundamental autoregressive generation loop.

A real GPT has additional architectural details, and some implementation choices vary, but this gives us the essential conceptual model.
