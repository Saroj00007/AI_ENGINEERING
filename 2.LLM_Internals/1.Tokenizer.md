# Phase 2 — Chapter 1: Tokenization

Welcome to **LLM Internals**. This is where we move from understanding neural networks generally to understanding what happens inside a language model.

Our first chapter is **Tokenization** because an LLM doesn't directly receive human text. Before anything like embeddings or attention can happen, the text has to be converted into something the neural network can process.

This follows our Phase 2 roadmap: **text → tokens → token IDs → vocabulary**, with BPE/subword tokenization as the key intuition. 

---

## 1. First principle: LLMs don't understand "words"

Suppose you give an LLM:

```text
I love AI
```

We humans see:

```text
"I"   "love"   "AI"
```

But the neural network doesn't receive those strings.

Ultimately, the model needs **numbers**.

So we need a pipeline:

```text
Human text
    ↓
Tokenization
    ↓
Tokens
    ↓
Token IDs
    ↓
Embeddings
    ↓
Neural network
```

Today we're focusing on the first three steps.

---

# 2. What is a token?

A **token is a piece of text that the tokenizer treats as one unit.**

Importantly:

> A token is **not necessarily a word**.

For example, conceptually:

```text
"I love AI"
```

could become:

```text
["I", " love", " AI"]
```

Notice something interesting.

The tokenizer might preserve the space as part of the next token:

```text
"I"
" love"
" AI"
```

So tokenization isn't simply:

```text
sentence → words
```

It's more like:

```text
sentence → pieces of text
```

Those pieces can be:

* whole words
* parts of words
* punctuation
* spaces
* numbers
* symbols
* sometimes individual characters

---

# 3. Why not simply tokenize by words?

You might initially think:

> "Why don't we just split the sentence by spaces?"

For example:

```text
"I love programming"
```

→

```text
["I", "love", "programming"]
```

That seems reasonable.

But consider:

```text
unhappiness
```

If the model has never seen `unhappiness` in its vocabulary, a word-based tokenizer has a problem.

It could represent it as:

```text
[UNKNOWN]
```

That's bad.

Now consider a subword approach:

```text
un + happiness
```

or perhaps:

```text
un + happi + ness
```

The model can still represent the word even if the exact word wasn't previously present as a single vocabulary item.

This is one of the major reasons modern tokenizers use **subword tokenization**.

---

# 4. Vocabulary

Now we need another concept:

### Vocabulary

A tokenizer has a predefined collection of tokens.

Imagine a tiny vocabulary:

```text
ID    Token
──────────────
0     <PAD>
1     <UNK>
2     I
3     love
4      AI
5     the
6     cat
7     ing
8     .
```

The important thing is that every token has an associated **integer ID**.

So:

```text
"I love AI"
```

might become:

```text
["I", " love", " AI"]
```

and then:

```text
[2, 3, 4]
```

The exact IDs are arbitrary. What matters is the mapping:

```text
token → integer ID
```

---

# 5. Why do we need token IDs?

Because neural networks operate on numerical representations.

We can't send:

```text
" love"
```

directly into a matrix multiplication.

We need:

```text
" love"
    ↓
token ID
    ↓
integer
    ↓
embedding vector
```

And **that embedding vector** is what will eventually enter the transformer.

So the complete pipeline begins to look like:

```text
"I love AI"
      ↓
Tokenizer
      ↓
["I", " love", " AI"]
      ↓
[2, 3, 4]
      ↓
Embedding lookup
      ↓
vectors
      ↓
Transformer
```

We'll study that embedding lookup in Chapter 2.

---

# 6. The important question: why subwords?

Let's use a concrete example.

Suppose our vocabulary contains:

```text
play
playing
played
player
```

A word-level tokenizer might need four separate vocabulary entries.

But a subword tokenizer could potentially represent them using pieces:

```text
play
ing
ed
er
```

Then:

```text
playing
```

could become:

```text
play + ing
```

and:

```text
player
```

could become:

```text
play + er
```

This gives the tokenizer a much more efficient vocabulary.

It also allows the model to handle unfamiliar words by breaking them into pieces it already knows.

---

# 7. BPE intuition

Our roadmap specifically includes **BPE/subword intuition**. 

BPE stands for:

**Byte Pair Encoding**

Don't worry about implementing the full algorithm yet.

The intuition is what matters.

Imagine initially having small pieces:

```text
h
e
l
l
o
```

The tokenizer learns that certain pieces frequently occur together.

For example:

```text
h + e → he
l + l → ll
```

Eventually it can form larger pieces:

```text
he
ll
o
```

And common words or word fragments can become single tokens.

So BPE is essentially finding useful reusable subword pieces.

---

# 8. A very important consequence

Tokenization means:

> **The model does not operate directly on characters, words, or sentences. It operates on token representations.**

This has practical consequences.

For example:

```text
"hello"
```

might be one token.

But:

```text
"unbelievable"
```

might be multiple tokens.

And:

```text
"hello!!!"
```

could be broken into several tokens because punctuation may have its own representation.

Therefore:

### Text length ≠ token length

This becomes extremely important later when we discuss:

* context windows
* token costs
* model latency
* prompt design
* RAG chunk sizes
* API pricing

We'll revisit this heavily in Phase 3 and Phase 4.

---

# 9. One subtle but important point

Don't think:

> "The model sees token ID 4837 and knows that 4837 means the word `hello`."

The **token ID itself has no semantic meaning**.

For example:

```text
hello → 4837
```

The number `4837` isn't meaningful.

It's essentially an **index** into the model's vocabulary/embedding table.

Later:

```text
4837
 ↓
embedding lookup
 ↓
[0.12, -0.45, 0.83, ...]
```

**That vector representation** is what becomes useful to the neural network.

This distinction will become extremely important in Chapter 2.

Remember what we learned about neural networks:
